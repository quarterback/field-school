# East Detroit resident UI — agent instructions

These rules apply to all work in this directory.

1. Read [CONTENT_STANDARDS.md](CONTENT_STANDARDS.md) before changing any public, login, or resident-facing copy. The PlainLanguage.gov guidance linked there is mandatory. For any UI work, also read the [AntiSlopUI skill](https://github.com/Vanszs/AntiSlopUI/blob/main/SKILL.md) and its relevant pattern catalogue entries. Apply its review and audit framework while keeping East Detroit's established municipal brand and the higher-priority project rules.
2. Read the actual component before proposing new wording. Edit the public homepage, login, dashboard, service panels, notices, empty states, and form controls in context. Do not invent features or decisions.
3. Write for residents completing real tasks. Say who did what, what changed, and what the resident can do next. Use short sentences, direct verbs, and familiar service names.
4. Use `prosekeep`, `plain-as-day`, and `red-pen-editor` editorial checks if the tools are available, and always review the final text manually against the plain-language test in CONTENT_STANDARDS.md.
5. Preserve the existing East Detroit brand, navigation, accessibility, realistic service records and institutional boundaries. Avoid classroom disclaimers and vendor jargon on normal resident pages. The sample account picker must still say that it is a sample and must not imply real authentication.
6. Do not add dividers, generic status cards, invented IDs, or decorative sections to compensate for unclear copy.
7. Do not treat a code build as a content or UI audit. Check the sign-in page, task flows, forms and resident screens. Report PASS, FAIL, N-A or UNVERIFIED for AntiSlopUI audit items, citing code or browser evidence. Confirm residents understand the next step and that each status matches actual UI behavior. Do not mark untested items as PASS.

Residents should never have to understand the application's architecture to use a city service.
